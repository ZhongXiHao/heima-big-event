# 代码优化建议

> 这份文档记录了一次代码走查中发现的可改进点，按"真实 bug → 死代码/未接线的部分 → 重复代码可提取 → 设计/风格可以更优雅"的顺序排列，方便按优先级处理。每一项都标了具体文件和行号，属于建议清单，不代表都要马上改。

## 1. 真实 bug（建议优先处理）

### 1.1 `AliOssUtil` 上传失败时仍然返回"成功" URL
`src/main/java/com/cshlands/utils/AliOssUtil.java:39-63`

```java
try (OSSClient client = clientBuilder.build()) {
    ...
    PutObjectResult result = client.putObject(...);
    ...
} catch (Exception e) {
    System.out.printf("error:\n%s", e);   // 异常被吞掉，只打印
}
return url;   // 不管有没有上传成功，都返回拼好的 URL
```
如果上传过程中抛异常（网络问题、凭证过期、bucket 权限等），这里只是打印错误，方法依然把提前拼好的 `url` 返回给调用方（`FileUploadController`），前端会拿到一个"上传成功"的响应和一个指向不存在文件的 URL。建议异常往上抛（或者返回 `null`/抛 `BusinessException`），让 `FileUploadController` 能感知失败并返回错误响应，而不是静默成功。

### 1.2 `ArticleVO` / `UserVO` 的时间字段没有统一格式，和文档约定不一致
- `src/main/java/com/cshlands/vo/ArticleVO.java:18-19`
- `src/main/java/com/cshlands/vo/UserVO.java:16-17`
- 对比 `src/main/java/com/cshlands/vo/CategoryVO.java:16-19`（这里加了 `@JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss")`）

`CategoryVO` 的 `createTime`/`updateTime` 单独加了 `@JsonFormat` 注解，但 `ArticleVO` 和 `UserVO` 没有，项目里也没有全局 Jackson 日期格式配置（`application.yml` 里没有 `spring.jackson.date-format`，代码里也没有对应的 `ObjectMapper` 配置）。结果是三种资源返回的时间字符串格式不统一，且不符合接口文档"时间格式为 `yyyy-MM-dd HH:mm:ss`"的约定（见 `docs/大事件接口文档-RESTful版.md:49`）。

更优雅的做法：不要在每个 VO 的每个字段上重复加注解，而是在 `application.yml` 加一行全局配置：
```yaml
spring:
  jackson:
    date-format: yyyy-MM-dd HH:mm:ss
    time-zone: GMT+8
```
然后把 `CategoryVO` 上现在这两个 `@JsonFormat` 也一并删掉，全项目统一由全局配置兜底。

## 2. 死代码 / 没有真正接上的部分

- **`LoginDTO`**（`src/main/java/com/cshlands/dto/LoginDTO.java`）：空类，全项目没有任何地方引用，可以直接删除。
- **`RegisterDTO`**（`src/main/java/com/cshlands/dto/RegisterDTO.java`）：定义好了校验规则，但 `AuthController.register` 实际上还是用零散的 `@Pattern` 参数（`src/main/java/com/cshlands/controller/AuthController.java:27-34`），没有真正用上这个 DTO。
- **`ArticleListDTO`**（`src/main/java/com/cshlands/dto/ArticleListDTO.java`）：全项目没有任何地方引用，`ArticleController.getArticles` 用的是单独的 `@RequestParam`（`src/main/java/com/cshlands/controller/ArticleController.java:30-34`）。
- **`UpdateUserDTO.avatar` 字段**（`src/main/java/com/cshlands/dto/UpdateUserDTO.java:18`）：定义了但从未被读取或写入（头像更新走的是单独的 `UpdateAvatarDTO` / `/me/avatar` 接口），属于遗留字段。
- **pom.xml 里的 `io.jsonwebtoken` 系列依赖**（`pom.xml:64-78`，`jjwt-api`/`jjwt-impl`/`jjwt-jackson`）：全项目没有任何地方 import 这三个包，实际生成/校验 JWT 用的是 `com.auth0:java-jwt`（`JwtUtil.java`）。这三个依赖属于选型切换后遗留的死依赖，可以删除，减少构建体积和潜在的依赖冲突面。

这几处和 `docs/大事件接口文档-RESTful版.md` 附录 B（"前后端改动清单"）里提到的"登录、注册改为 `@RequestBody` + DTO"是同一件事——DTO 已经建好，但 `AuthController` 还没有切过去，可以作为后续把 `AuthController` 迁移到 REST 风格时的一部分顺手做掉。

## 3. 重复代码可以提取

### 3.1 `getCurrentUserId()` 在多处重复
- `src/main/java/com/cshlands/service/serviceImpl/ArticleServiceImpl.java:99-102`
- `src/main/java/com/cshlands/service/serviceImpl/CategoryServiceImpl.java:97-100`
- `UserServiceImpl` 里也有三处内联的同样写法（`UserServiceImpl.java:55`、`:69`、`:80`）

都是这几行：
```java
Map<String, Object> claims = ThreadLocalUtil.get();
Integer id = ((Number) claims.get("id")).intValue();
```
建议把它收敛成 `ThreadLocalUtil` 上的一个静态方法，例如：
```java
public static Integer getCurrentUserId() {
    Map<String, Object> claims = get();
    return ((Number) claims.get("id")).intValue();
}
```
这样所有 ServiceImpl 都调用 `ThreadLocalUtil.getCurrentUserId()`，既减少重复，也避免了以后有人在某一处漏写 `.intValue()` 或者用错 key（比如之前遇到的 `(Integer) claims.get("id")` 强转在 `UserServiceImpl.updateUserInfo`/`updateUserAvatar` 里其实是不安全的写法，`Number` 强转更稳）。

### 3.2 `getOwnedCategoryOrThrow` 在两个 ServiceImpl 里逐字重复
- `src/main/java/com/cshlands/service/serviceImpl/ArticleServiceImpl.java:104-110`
- `src/main/java/com/cshlands/service/serviceImpl/CategoryServiceImpl.java:89-95`

两处实现完全一样："按 id 查分类，如果不存在或不属于当前用户就抛 404"。`ArticleServiceImpl` 依赖这个方法只是为了在建文章时校验 `categoryId` 属于当前用户，本质上是 `CategoryService` 的职责。建议把这个校验方法上移到 `CategoryService` 接口（例如 `Category getOwnedCategoryOrThrow(Integer categoryId)`），`ArticleServiceImpl` 直接注入 `CategoryService` 调用，而不是自己在 `ArticleServiceImpl` 里再实现一遍——这样以后分类归属的判定逻辑只有一处，不会出现两边改一处漏改的情况。

## 4. 设计/风格上可以更优雅的地方（优先级较低，属于打磨项）

- **`@Options(useGeneratedKeys = true, keyProperty = "id")` 被误加到了 SELECT/UPDATE 语句上**：
  - `ArticleMapper.selectByIdAndUser`（`src/main/java/com/cshlands/mapper/ArticleMapper.java:19-22`）
  - `ArticleMapper.updateArticle`（同文件 `:24-27`）
  - `CategoryMapper.updateById`（`src/main/java/com/cshlands/mapper/CategoryMapper.java:21-23`）

  这个注解只对 `INSERT` 语句有意义（回填数据库生成的自增主键），写在 `@Select`/`@Update` 上没有实际效果，应该是从 `insert` 方法复制粘贴时带过来的，建议删掉以免误导后来者以为这里也在做主键回填。

- **`UserMapper` 的更新语句按 `username` 做 WHERE 条件，而不是按主键 `id`**（`src/main/java/com/cshlands/mapper/UserMapper.java:21-33`，`updateUserInfo`/`updateUserAvatar`/`updateUserPassword` 三个方法）：调用方（`UserServiceImpl`）其实已经通过 `findById` 拿到了完整的 `User`（带 `id`），按主键 `id` 更新比按 `username` 更直接、走主键索引也更快，也避免"以后允许改用户名"这类需求下 WHERE 条件失效的问题。

- **`Result` 类手写 getter/setter，和项目里其它类风格不一致**（`src/main/java/com/cshlands/pojo/Result.java`）：项目里 DTO/VO/POJO 基本都用 Lombok（`@Data`/`@Getter`/`@Setter`），只有 `Result` 是手写的，改成 `@Data` 可以少十几行样板代码。

- **`AliOssUtil` 的配置硬编码 + 每次上传都新建客户端**（`src/main/java/com/cshlands/utils/AliOssUtil.java`）：
  - `ENDPOINT`/`REGION`/`BUCKET` 硬编码在方法内的局部常量里，建议像 `JwtUtil` 一样用 `@Value` 从 `application.yml` 注入，方便不同环境切换。
  - 每次调用 `execute` 都 `OSSClient.newBuilder()...build()` 新建一个客户端，`OSSClient` 属于可以复用的重量级资源，更合适的做法是把它做成 Spring 管理的单例 `@Bean`，注入到 `AliOssUtil`（或者把 `AliOssUtil` 也改造成 `@Component` 而不是纯静态类）。
  - 方法体里还留了一行没用到的 `String data = "hello world";` 和几处注释掉的调试代码（`:23`、`:33-35`、`:42`），可以一并清理。

- **`ArticleStateTypeHandler.setNonNullParameter` 方法签名里重复声明了同一个异常**（`src/main/java/com/cshlands/mapper/handler/ArticleStateTypeHandler.java:17`）：
  ```java
  public void setNonNullParameter(...) throws SQLException, SQLException {
  ```
  多写了一次 `SQLException`，虽然能编译通过，但属于明显的笔误，建议清理成一个。

## 优先级小结
1. **先处理**：1.1（OSS 上传失败静默返回成功）、1.2（时间格式不统一）——这两个会直接影响接口行为/前端展示。
2. **顺手清理**：第 2 节的死代码（尤其是 pom.xml 里两个用不到的 JWT 依赖），风险低、收益明确。
3. **有空再做**：第 3 节的重复代码提取——不影响正确性，但会让以后同类逻辑改动更省心。
4. **打磨项**：第 4 节，都是不影响功能的风格/清晰度问题，可以在顺手碰到对应文件时一起改。
